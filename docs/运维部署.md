# 运维部署手册（生产环境）

> 适用对象：负责把 Leadhub（WhatsApp BSP 商机线索系统）部署到生产的运维/开发。
> 所有配置项以 `backend/app/core/config.py` 为准，命令以根目录 `Makefile` 为准——本文没有臆造的配置名。
> 快速上手（本地开发）看 [README](../README.md)，界面操作看 [使用手册](使用手册.md)；本文只讲生产。

---

## 1. 部署架构

### 1.1 单进程是硬约束，不是建议

系统采用 **DB 即队列**（无 Celery / Redis）的设计：API 服务、采集任务执行器（`app/services/task_runner.py`）、APScheduler 定时调度器（`app/services/scheduler.py`）跑在**同一个进程**里。

原因（见 `backend/app/main.py` lifespan）：

- 取消事件（cancel_event）和实时进度存在**进程内存**，DB 队列没有行锁；
- `WORKERS > 1` 时多个进程会互相把对方 `running` 的任务判 `failed`、取消跨进程失效。

因此 `main.py` 在 `WORKERS > 1` 时**直接禁用任务执行与调度**（启动日志出现
`⚠️ WORKERS=N > 1：任务执行器与定时调度已禁用（DB 队列单进程设计）。采集任务将保持 queued 状态`），
任务全部卡在 `queued`。

结论：

| 部署形态 | 要求 |
|---|---|
| 承担任务执行的实例 | **`WORKERS=1`**（uvicorn 单进程，或 gunicorn `-w 1`） |
| 纯 API 实例（可选） | `WORKERS` 可调大（任务执行自动禁用），不跑调度 |
| `SCHEDULER_ENABLED=true` | 只在**一个** `WORKERS=1` 的实例上开 |

⚠️ **Docker 部署陷阱**：`backend/docker/Dockerfile` 的 ENTRYPOINT 是
`gunicorn ... -w "${WORKERS:-4}"`——**默认 4**。必须确保 `backend/.env` 里显式写 `WORKERS=1`
（compose 的 `env_file: ./backend/.env` 会传进容器），否则容器起来任务永远 queued。

### 1.2 推荐拓扑（单机）

```
浏览器 ──HTTPS──▶ nginx（443，静态 + 反代）
                    │
                    ├── /            → frontend/dist 静态文件（pnpm build 产物）
                    └── /api/        → 127.0.0.1:8000 后端（单进程）
                                          │
                                          └── PostgreSQL 16（容器或独立实例）
```

- 后端：Docker Compose（`docker-compose.yml` 的 `backend` + `postgres` 服务），
  或裸机 venv + gunicorn（`WORKERS=1`）。
- 数据库：生产**必须 PostgreSQL**（`DB_TYPE=postgresql`）；SQLite 只适合本地体验。
- adminer（8080）是开发用的数据库 UI，**生产不要暴露公网**（不启或防火墙/仅内网）。

### 1.3 吞吐不足时的扩容路径

按成本从低到高：

1. **垂直扩容（首选）**：加 CPU / 内存；调大 `DB_POOL_SIZE`（默认 10）与
   `DB_MAX_OVERFLOW`（默认 20）；采集吞吐调 `COLLECT_MAX_CONCURRENT`（默认 2，
   即采集 worker 协程数）与 `ENRICH_CONCURRENCY`（默认 5）。
2. **API 横向扩容**：加几台纯 API 实例（`WORKERS` 可 >1，任务执行自动禁用）挂负载均衡；
   保留**恰好一台** `WORKERS=1` 实例跑任务执行 + 调度。
   注意：取消与实时进度存在执行实例内存里，多实例下「取消任务」请求需要路由到执行实例才生效
   （API 实例上调用取消会返回成功但实际不会中断）。
3. **拆独立 worker 进程**：把任务执行器拆成独立进程部署后再调大 `WORKERS`（需要改造，
   见 `config.py` 中 WORKERS 注释）。

## 2. 首次上线 checklist

### 2.0 把代码放到服务器（第一次部署时执行一次）

```bash
cd /srv                                # 放系统的目录（下文所有路径都以 /srv/youzi-leadhub 为准）
git clone git@github.com:youzilovezp/youzi-leadhub.git
cd youzi-leadhub                       # 之后本文所有 make 命令都在这个目录里执行
```

- 服务器没配 GitHub SSH 密钥（报 `Permission denied (publickey)`）时，改用
  `git clone https://github.com/youzilovezp/youzi-leadhub.git`，效果一样。
- 服务器完全连不上 GitHub 时：先在自己电脑上克隆，再把整个 `youzi-leadhub` 文件夹上传到服务器 `/srv/` 下。
- 换目录也行（如 `/opt`），但后文 nginx 的 `root /srv/youzi-leadhub/frontend/dist` 与备份脚本的 `cd /srv/youzi-leadhub` 要跟着改。

### 2.1 环境变量（backend/.env）

复制 `backend/.env.example` 为 `backend/.env` 后逐项核对：

**必改（安全红线）**

| 变量 | 要求 | 不满足的后果 |
|---|---|---|
| `SECRET_KEY` | `openssl rand -hex 32` 生成，**≥32 字符** | 启动即失败（pydantic `min_length=32`） |
| `INITIAL_ADMIN_PASSWORD` | 强密码（建议 ≥16 位随机）。prod 下 `admin`/`password`/`123456`/`admin123`/`changeme` 会**拒绝启动**（`main.py _check_prod_secrets` → `SystemExit(1)`） | 启动中止，日志见「生产环境检测到默认弱密码」 |
| `APP_ENV` | `prod` | `/docs`、`/redoc`、`/api/v1/openapi.json` 不会禁用，schema 全量暴露给匿名用户；HSTS 不下发 |
| `DEBUG` | `false` | `DEBUG=true` 时即使 `APP_ENV=prod` 也会重新放开 /docs |
| `TRUSTED_HOSTS` | 加入真实域名，如 `["lead.example.com","localhost","127.0.0.1"]` | nginx 部署后所有请求 400 `Invalid host header`（TrustedHostMiddleware） |
| `CORS_ORIGINS` | 显式列出前端可信来源（含协议），留空 = 拒绝所有跨域 | 前端跨域登录失败 |
| `AUTO_SEED_DATA` | `false`（dev 默认 true 会写入 manager/alice/bob 三个 Demo@123 账号） | 公开凭据进生产库。注：`APP_ENV=prod` 时本来就不建 demo 用户，但仍建议显式置 false |

**按需（业务开关，全量见 [backend/docs/配置说明.md](../backend/docs/配置说明.md)）**

- `AUTO_INIT_DB`（默认 `true`）：启动时自动建表 / `alembic upgrade head`，升级即迁移，生产建议保持
- `SCHEDULER_ENABLED=true`：cron 定时调度，只在一个 `WORKERS=1` 的实例上开
- `META_ADS_ACCESS_TOKEN`：`meta_ads` 采集器必填（免费申请：https://www.facebook.com/ads/archive/api ）
- `SEARCH_ENGINE`：默认 duckduckgo 零 key（DDG 连不上时自动降级必应中国版 `bing_cn` 直连）；也可直接设为 `bing_cn`（国内直连零依赖）；生产推荐自托管 SearxNG 配 `SEARXNG_URL`
- `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`：OpenAI 兼容协议，不配置则降级规则模板；零成本方案指向本地 Ollama
- `LOG_LEVEL` / `LOG_FORMAT`：生产建议 `INFO` + `json`（进 ELK/Loki）
- `COLLECT_MAX_CONCURRENT` / `COLLECT_TASK_TIMEOUT` / `ENRICH_CONCURRENCY`：采集吞吐（默认 2 / 3600s / 5）

### 2.2 数据库准备

```bash
# 方式 A：Docker Compose 起 PG + 后端（会自动建用户/库/表 + 种子角色与 admin）
docker compose --env-file ./backend/.env up -d --build

# 方式 B：复用已有 PostgreSQL
#   先在 PG 里建好 .env 对应的用户/库：
#     create user "youzi-leadhub" with password '<POSTGRES_PASSWORD>';
#     create database "youzi-leadhub" owner "youzi-leadhub";
#   再启动后端（表结构与迁移在启动时由 AUTO_INIT_DB 自动完成）
```

启动时 `init_db()` 的行为（`backend/app/db/init_db.py`）：

- 首次启动（无 `alembic_version` 表）：`create_all` + `stamp head`；
- 后续启动：`alembic upgrade head`（升级发布时**无需手工跑迁移**）；
- 任何步骤失败只告警不阻塞启动（所以「连不上库也能起进程」，要用 `/readyz` 判断真实状态）；
- 种子数据：admin + 5 个内置角色**始终创建**（不受 `AUTO_SEED_DATA` 影响）；demo 用户仅
  `APP_ENV != prod` 且 `AUTO_SEED_DATA=true` 时创建。

### 2.4 nginx 反代配置示例（含 HTTPS 与 X-Forwarded-For）

前端 `pnpm build` 产物在 `frontend/dist`（`VITE_API_BASE_URL=/api/v1` 相对路径，
Vue Router history 模式需要 `try_files` 回退）。

```nginx
# /etc/nginx/conf.d/leadhub.conf
server {
    listen 80;
    server_name lead.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name lead.example.com;

    ssl_certificate     /etc/nginx/certs/lead.example.com.pem;      # 证书（Let's Encrypt / 云厂商）
    ssl_certificate_key /etc/nginx/certs/lead.example.com.key;

    client_max_body_size 20m;

    # ---- 前端静态资源 ----
    root /srv/youzi-leadhub/frontend/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;    # history 路由回退
    }

    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # ---- 后端 API 反代 ----
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        # ⚠️ 登录限流（auth_service._client_ip）按 X-Forwarded-For **首跳**取客户端 IP。
        #    单层反代建议直接覆盖为 $remote_addr，防止客户端伪造 XFF 绕过限流；
        #    若上面还有 LB，需由 LB 清洗后再追加（proxy_add_x_forwarded_for）。
        proxy_set_header X-Forwarded-For $remote_addr;
        # ⚠️ TrustedHostMiddleware 校验 Host——必须传，否则 400 Invalid host header
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 120s;             # 与后端 gunicorn --timeout 120 对齐（CSV 导出/长查询）
        proxy_send_timeout 120s;
    }

    # 健康检查（可只放行给监控网段）
    location ~ ^/(healthz|readyz)$ {
        proxy_pass http://127.0.0.1:8000;
        access_log off;
    }
}
```

要点：

- **必须传 `X-Forwarded-For`**：后端登录暴力破解限流按它识别客户端；
  不传则所有请求共用 nginx 的 IP，一个用户触发锁定会连坐所有人。
- **必须传 `Host`**：后端 `TRUSTED_HOSTS` 校验失败直接 400。
- 生产 `APP_ENV=prod` 时后端会自动下发 `Strict-Transport-Security` 等安全 header，
  nginx 侧不必重复添加。

### 2.5 健康检查

| 端点 | 语义 | 用途 |
|---|---|---|
| `GET /healthz` | 进程级（只要进程能响应就 200） | liveness / 容器 HEALTHCHECK（Dockerfile 用的就是它） |
| `GET /readyz` | 含 DB ping（`SELECT 1`），DB 挂返回 **503** | readiness / 负载均衡摘除 |

```bash
curl -fsS https://lead.example.com/readyz
# {"status":"ready","database":"ok"}
```

监控建议：对 `/readyz` 做 1 分钟级探测，503 告警；同时盯日志里的
`auth.login.fail`（暴力破解）与 `collect-worker` 异常堆栈。

### 2.6 上线前最后确认

- [ ] `WORKERS=1`（容器内也生效）
- [ ] `make admin-pass NEW='<强密码>'`（或确保 `INITIAL_ADMIN_PASSWORD` 是强密码）后能登录
- [ ] `APP_ENV=prod` 下访问 `/docs` 返回 404（确认 schema 已禁用）
- [ ] 用真实域名登录一次（验证 TRUSTED_HOSTS / CORS / X-Forwarded-For 三件事）
- [ ] 建一个普通销售账号验证数据权限（own 级看不到别人的线索）
- [ ] 跑一次小规模采集任务，确认状态能从 queued → running → completed

## 3. 日常运维

### 3.1 备份与恢复

```bash
make backup                              # 备份 → backups/app_YYYYMMDD_HHMMSS.sql（PG 用 pg_dump）
make restore FILE=backups/app_xxx.sql    # 恢复（⚠️ 先 DROP SCHEMA public 清空目标库再导入）
```

- `make backup` 逻辑（Makefile）：Docker PG 在跑则 `docker compose exec postgres pg_dump`；
  否则用本机 `pg_dump` 连 `127.0.0.1:$POSTGRES_PORT`（需要装 PostgreSQL 客户端工具）。
  SQLite 模式则是复制 `backend/data/app.db`（恢复后**必须重启后端**，旧进程持有文件句柄）。
- `make restore` 是**破坏性操作**：会 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`
  后再导入。只用于整库恢复，执行前先 `make backup` 留当前状态快照。
- 所有 make 目标须在**仓库根目录**执行（Makefile 从 `backend/.env` 读连接信息）。

### 3.2 cron 自动备份 + 异地存储（建议）

`backups/*.sql` 是明文 pg_dump，含全部 PII（见 §5）。建议：加密后再出机器、滚动保留。

```bash
# crontab -e（root 或项目用户），每天 03:15 备份 + 加密 + 上传
15 3 * * * cd /srv/youzi-leadhub && make backup >> backups/backup.log 2>&1 && \
  f=$(ls -t backups/*.sql 2>/dev/null | head -1) && \
  openssl enc -aes-256-cbc -pbkdf2 -in "$f" -out "$f.enc" \
    -pass file:/etc/leadhub/backup.key && rm -f "$f" && \
  rclone copy "$f.enc" remote:leadhub-backups/$(hostname)/ && \
  find backups/ -name '*.enc' -mtime +30 -delete
```

- 密钥文件 `/etc/leadhub/backup.key` 权限 `600`，与备份分开存放；恢复时
  `openssl enc -d -aes-256-cbc -pbkdf2 -in x.sql.enc -out x.sql -pass file:/etc/leadhub/backup.key`。
- 异地存储（rclone → S3/OSS/另一台机房机器）至少一份；保留策略示例：日备 30 天 + 月备 12 个月。
- 每季度做一次恢复演练（拿到加密文件 → 解密 → `make restore` 到测试库）。

### 3.3 升级发布流程

```bash
cd /srv/youzi-leadhub
make backup                                  # 1. 升级前备份（必做）
sudo systemctl stop youzi-leadhub            # 2. 停服务（Docker 模式：docker compose --env-file ./backend/.env stop backend）
git pull                                     # 3. 拉代码
docker compose --env-file ./backend/.env up -d --build backend   # 4a. Docker 模式重建
# 4b. 裸机模式：
#     cd backend && . .venv/bin/activate && pip install -e . && \
#     gunicorn app.main:app -w 1 -k uvicorn.workers.UvicornWorker -b 0.0.0.0:8000
curl -fsS http://127.0.0.1:8000/readyz       # 5. 健康检查（等 database: ok）
```

- **迁移自动跑**：启动时 `AUTO_INIT_DB=true` 会执行 `alembic upgrade head`，
  无需手工干预；要手工验证可 `make db-upgrade`。
- 回滚：`git checkout <上一个 tag/commit>` 重建 + `make restore FILE=<升级前备份>`
  （注意 restore 是清库导入，只在升级引入了不兼容迁移时才用）。
- 不要在生产使用 `make db-downgrade`（会 drop 上一 migration 的对象，Makefile 自带交互确认）。

## 4. 故障处理 runbook

### 4.1 采集任务一直卡在 queued

**排查顺序：**

1. **看后端启动日志有没有这句**：
   `⚠️ WORKERS=N > 1：任务执行器与定时调度已禁用（DB 队列单进程设计）`
   → 有：`backend/.env` 改 `WORKERS=1`，重启实例（Docker 部署尤其注意 Dockerfile 默认 `-w 4`）。
2. **cron 任务**：`SCHEDULER_ENABLED=false` 时 cron 任务不会触发（手动「执行」仍可跑）。
   需要定时则设 `true` 并重启（只对一个 WORKERS=1 实例生效）。
3. **并发闸门满**：`COLLECT_MAX_CONCURRENT`（默认 2）个 worker 都在跑长任务时，
   新任务排队是**正常行为**——看任务列表里是否有 running 的任务占着坑。
4. **实例刚重启过**：重启会把中断的 running 任务重置为 failed（错误信息
   「进程重启，任务中断」），重新点「执行」即可。

**定位 SQL：**

```sql
SELECT id, name, collector, status, cron_expr, enabled, created_at, started_at
FROM collect_tasks
WHERE status IN ('queued', 'running')
ORDER BY id;
```

**重新入队**：`POST /api/v1/collect/tasks/{task_id}/run`（超管 token），或任务列表页「执行」。

### 4.2 登录被锁（「登录尝试过于频繁，请 N 秒后再试」）

机制（`app/services/auth_service.py`）：DB 表 `login_throttles` 计数——

- `u:<用户名小写>|ip:<IP>` 连续 **5** 次失败 → 锁定；
- `ip:<IP>` 任意用户名累计 **20** 次失败 → 锁定；
- 锁定时长 60s 起指数翻倍、封顶 1 小时；**登录成功自动清零**。

解锁（对 PG 执行）：

```sql
-- 1. 先看现状
SELECT throttle_key, fail_count, locked_until FROM login_throttles ORDER BY locked_until DESC;

-- 2a. 解锁单个用户（key 里的用户名是小写）
DELETE FROM login_throttles WHERE throttle_key = 'u:zhangsan|ip:203.0.113.10';

-- 2b. 解锁某个来源 IP 的全部记录
DELETE FROM login_throttles WHERE throttle_key LIKE '%|ip:203.0.113.10' OR throttle_key = 'ip:203.0.113.10';

-- 2c. 全清（影响所有登录限流，仅确认无攻击时用）
DELETE FROM login_throttles;
```

**如果大量用户同时被锁**：多半是 nginx 没传 `X-Forwarded-For`，所有人共用 nginx IP——
按 §2.4 修 nginx 后清表。若是真实攻击（单一 IP 高频失败），保留记录并配合防火墙封源 IP。

### 4.3 常见启动失败

| 症状（日志关键词） | 原因 | 处理 |
|---|---|---|
| `生产环境检测到默认弱密码 INITIAL_ADMIN_PASSWORD=...` 后进程退出 | `APP_ENV=prod` 且初始密码在弱密码表 | 改 `backend/.env` 强密码，或 `make admin-pass NEW='...'`（改的是 DB 里的 admin）后重启 |
| 启动即崩，pydantic `ValidationError` 指向 `SECRET_KEY` | 缺失或 <32 字符 | `echo "SECRET_KEY=$(openssl rand -hex 32)"` 写入 .env |
| `数据库密码认证失败` / `connection refused` / `数据库不存在`（init_db 的中文诊断） | PG 没起 / `.env` 连接信息不对 / 库没建 | `make start` 起中间件；核对 `POSTGRES_HOST/PORT/USER/PASSWORD/DB`；旧 Docker 卷密码不匹配时 `docker compose down --volumes` 重建（⚠️ 清卷，先备份） |
| 进程起来了但 `/readyz` 503 `database: down` | DB 连接失败**不会阻塞启动**（init_db 只告警） | 同上修 DB；修好前负载均衡应已按 503 摘除 |
| `迁移报「对象已存在」`（alembic already exists） | alembic 版本与实际表结构错位（手动改过库） | 备份后重置迁移状态：`make stop && docker compose down --volumes && make start`（清库操作，先 `make backup`） |
| 通过域名访问全部 400 `Invalid host header` | `TRUSTED_HOSTS` 没加真实域名 | .env 的 `TRUSTED_HOSTS` 加域名重启 |
| `web_search` 任务 failed | 引擎选了 google_cse/bing 未配凭据，或 DDG 被限流 | 用默认 duckduckgo；生产自托管 SearxNG 抗限流 |

### 4.4 其他

- **忘了 admin 密码**：`make admin-pass NEW='<新强密码>'`（重置 DB 里的 admin，不需要旧密码）。
- **token 撤销**：登出即把 jti 写入 `token_blacklist`；怀疑 token 泄露时可清空该表强制全员重新登录
  （`DELETE FROM token_blacklist;` 会让已登出 token 复活，仅在确认无风险时用，更稳妥的是轮换 `SECRET_KEY` 重启）。
- **CSV 导出超时**：导出上限 `limit=50000`、流式分批产出；调大 nginx `proxy_read_timeout`
  与后端 gunicorn `--timeout`（默认 120s）。

## 5. PII 与数据合规

> 需求红线：**联系人仅限合法来源**。本章是操作层面的最低要求。

### 5.1 当前系统存储的个人数据范围

| 表 | 字段 | 说明 |
|---|---|---|
| `leads` | `phone_raw` / `phone_e164` / `whatsapp_numbers` / `email` / `address` / `social` | 企业电话（含 WhatsApp 号码）、公开邮箱、地址、社媒链接 |
| `lead_contacts` | `name` / `job_title` / `department` / `email` / `phone` / `linkedin` | **自然人联系人**的姓名、职位、邮箱、电话、LinkedIn |
| `lead_signals` | `value` / `evidence_url` / `evidence_raw` | 信号证据链（号码、命中页面 URL、原文片段） |
| `lead_follow_ups` | `note` | 销售跟进备注（可能含沟通内容） |
| `users` | `email` / `password_hash` | 员工账号（bcrypt 哈希） |

### 5.2 采集合规要求（红线）

- 数据来源仅限**公开网页/公开 API**：Meta 广告资料库（免费公开数据）、DuckDuckGo/SearxNG、企业官网
  （`meta_ads`，公开广告数据）、公开招聘页（`job_posting`）、目标公司官网公开内容
  （`website_enrich`，邮箱只取官网公开披露的）。
- **不得**接入需要登录/破解/购买的非公开渠道个人数据；新增采集器时评审数据来源合法性。
- 手工录入联系人也必须来自公开来源，销售不得录入私下获取且无授权的个人数据。
- WhatsApp 建联是**人工发起**：系统生成话术 → 人工审核 → 人工复制发送（`sales_messages`
  队列），不做自动群发——保持这一设计，勿加自动化外发。

### 5.3 数据保留策略（建议口径）

- 未成交且长期无活动的线索：**24 个月**未跟进且无成交商机的，归档或删除。
- 任务日志（`collect_task_logs`）：保留 6~12 个月即可，定期清理。
- 备份文件：按 §3.2 的滚动保留（如日备 30 天），到期删除——**删除生产数据不会同步删备份**，
  只能靠备份过期自然覆盖。

先查再删（PG）：

```sql
-- 候选：无成交商机 且 24 个月未跟进（从未跟进的按 updated_at 兜底）
SELECT l.id, l.name, l.last_followed_at, l.updated_at
FROM leads l
LEFT JOIN opportunities o ON o.lead_id = l.id AND o.stage = 'won'
WHERE o.id IS NULL
  AND COALESCE(l.last_followed_at, l.updated_at) < now() - interval '24 months';
```

删除**走 API 而不是手工 SQL**（保证关联表清干净）：

```
DELETE /api/v1/collect/leads/{id}      # 超管 token
```

该端点会显式删除该线索的 `lead_contacts` / `lead_events` / `lead_follow_ups`，
PostgreSQL 下 `lead_signals` / `sales_messages` / `opportunities` 由外键
`ondelete=CASCADE` 一并清除。批量场景用超管 token 写脚本循环调用。

### 5.4 用户（数据主体）要求删除时

1. 用企业名/域名/电话在系统里定位线索（列表页关键词或 `GET /api/v1/collect/leads?keyword=`）。
2. 超管执行 `DELETE /api/v1/collect/leads/{id}`（级联口径见上）。
3. **登记**该请求（时间、请求人、处理的线索 id）——用于应对后续审计询问。
4. 备份里的残留：记录删除日期，等含该数据的备份按保留期滚动过期；若备份保留期很长，
   需评估对备份做同等删除或接受「备份按期失效」的口径并在登记中注明。
5. 如该联系人曾出现在导出的 CSV 里，追溯分发范围并通知销毁。

### 5.5 备份加密与访问控制

- `backups/*.sql` 为明文全量导出，**必须**：加密后才出机器（§3.2 的 openssl / 或 gpg）、
  服务器本地 `chmod 600`、密钥与备份分离保存、异地存储的桶开最小权限 + 版本化。
- 生产服务器 SSH / 数据库端口不对公网开放；adminer（8080）生产不启。
- `.env`（含 `SECRET_KEY`、数据库密码、采集凭据）权限 `600`，永不入库 git。

### 5.6 导出审计（建议）

当前 `GET /api/v1/collect/leads/export`（CSV，36 个可选字段，含联系人姓名/邮箱/电话）
**没有内置审计表**。上线后至少做到：

- nginx 对该路径单独留 access log（谁、何时、导出多大），按月 review；
- 导出属于敏感操作，建议后续在代码里补一条审计事件（类似 `lead_events`），
  记录操作者 id + 筛选口径 + 行数；
- 内部制度上把「导出需主管审批」写进销售 SOP，系统外的 WhatsApp 建联话术同样留档在
  `sales_messages`（审核人/发送状态可追溯）。
