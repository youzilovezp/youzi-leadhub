## 2. 逻辑问题清单

### L1【A】§9「三类定时任务」漏掉 b2b_supplier——文档内部不一致

- **证据**：§9.2 写「配置三类定时任务（meta_ads / 招聘巡检 / 全库富化）」；实现 `seed_cron_tasks.py` 也只种 3 个 cron（meta_ads / job_posting / website_enrich）。而 b2b_supplier 是 2026-09-01 裁决新加的**第 6 个采集器**，且定位是「meta_ads token 未配置期间的主扩量通道」（FR-1.6）。
- **问题**：token 缺失时主扩量靠 b2b，但初始化脚本和运营手册都不给 b2b 定时任务——「每天收到一批」在主扩量通道上没有定时保障，运营靠手动建任务。
- **结论**：§9.2 改为四类（+ b2b 目录采集），`seed_cron_tasks.py` 同步补种；b2b 的 cron 建议错开 meta_ads 高峰。

### L2【A】whatsapp_gone 负证据不触发重评——分数与证据会长期脱钩

- **证据**：实现注释明写「不翻 whatsapp_hit 布尔列（历史事实保留、**评分不动**），只发 whatsapp_gone 事件进时间线」（`website_enrich.py:1797-1809`）；FR-1.5 只定义「证据展示 N 天未复现（≥90 天标注）」，未定义分数动作。
- **问题**：意向分语义是「**现在**有多需要你」（§3 FR-3）。官网 WA 入口消失（+25）或多分线减员（multi_numbers +10）后，分数永久保留旧证据，S/A 虚高进入今日商机；销售虽有事件提示，但列表排序、批次筛选、自动分配全按虚高分走。≥90 天未复现的线索没有任何分数衰减机制。
- **结论**：建议追加裁决：whatsapp_gone 事件发生后，线索下次被富化触发重评时按「当前可复现证据」重算对应信号分（不翻历史事件，只翻当前分数——与「不翻历史布尔」的初衷不冲突）。最小改法：`apply_score` 输入里 WA 类信号以「最近复现时间」为口径。

### L3【B】S+A 占比目标线 20% 与里程碑 5–10% 口径张力

- **证据**：§7 数据质量「S+A 占比 ≥20%」；§7 里程碑「1 万家种子 → 筛出 500–1000 个 S/A（5–10%）即模型验证成立」。实现：看板 `sa_ratio = (S+A) / 全池`（池 = 非 foreign/non_buyer，`quality.py:221-231`）。
- **问题**：若 1 万种子全部入池，里程碑达成时（5–10%）看板必然红（<20%）。两个数字一个是「模型成立线」、一个是「成熟质量线」，文档未区分阶段。
- **结论**：追加一句口径即可：20% 为**成熟期目标线**；冷启动验收以里程碑 5–10% 为准，看板分阶段阈值或标注「当前阶段」。

### L4【C】§4「手工编辑触发重评」超前于 V1 功能

- **证据**：§4「合并、富化、联系人变更、**手工编辑**均触发重评」；但手工编辑在 §8 V1.5 ②才做。V1 实现里重评触发点是合并/富化/联系人变更（`lead.py:291/511` 经 `rescore_and_log`）。
- **结论**：措辞同步——V1 触发点 = 合并/富化/联系人变更；手工编辑并入 V1.5。纯文档措辞，无逻辑冲突。

### L5【C】今日商机批次三来源的重叠语义——已实现，口径确认

- **证据**：实现 `promoted_set` 排除后取新线索（`collect.py:644-648`）；预警切片独立列出，同线索可同时出现在 promoted 行与 alerts 列表。
- **结论**：并集去重已做；「降级再升级」会在再次升级日重复入批——合理（信号增强值得再次触达）；预警与行区重复展示是信息冗余，无害。记录口径即可，无需改。

### L6【C】三问齐备门槛 why≥2 对 S/A 恒成立——防御性冗余，无副作用

- **证据**：`complete = len(why) >= 2 ∧ products ≥1 ∧ who 有任一`（`intent.py:170`），why 取 breakdown 明细 top-3（每信号一条）。单信号最高 40 分（ctwa_ad）< 60，因此任何 ≥60 分线索至少命中 2 条信号，why≥2 恒成立。
- **结论**：门槛不会误杀任何批次线索，属防御性一致校验。无需改；若未来出现 ≥60 的单信号（如信号分值调整），该门槛会自动生效，反而正确。

### L7【✓ 核实无问题】排除面 7 处 vs「过 ICP 门」的语义

- 一度怀疑：今日商机/预警/质检用 `icp_status.notin_(foreign, non_buyer)`（`collect.py:663`、`sales.py:83`、`quality.py:53`）会放进 cn_domestic/unknown，与「qualified 才进今日商机」矛盾。
- **核实**：§2.3 五态表语义是 foreign/non_buyer「**默认排除**」（icp=all 可显式看），排除面 = 排除这两态；cn_domestic 是培育池不是排除面。「今日商机」的 promoted/new 用 `== qualified`，预警切片用排除面口径——与 FR-6 原文「新增高分（qualified 且 ≥60）+ 高价值预警切片」一致：预警切片允许培育池线索因新信号被推给销售（正是培育池升级的通道）。**无问题**。

### L8【✓ 核实无问题】CSV 导出的 icp=all 与「排除面 CSV 导出」

- 导出 `icp=all` 显式不过滤、缺省排除 foreign/non_buyer（`collect.py:367-371`），与列表同口径。**无问题**。

### L9【✓ 核实无问题】「有评估结论」的判定口径

- 实现：`evaluated = enriched_at 非空（成功抓首页才写）或（meta_ads 来源且有官网）`（`icp.py:200`）。富化失败的线索不会误判 foreign，保持 unknown 保留翻案通道。与 §2.3 一致。**无问题**。

### L10【B】官网发现吞吐是冷启动的硬瓶颈（每轮固定 30）

- **证据**：FR-1.5「每轮上限 30、3s 间隔」；实现注释「每轮上限固定 30……想多补靠多轮，不靠一轮放大」（`website_enrich.py:863-867`）。全库扫描一轮至多发现 30 个官网；每日 cron 一轮 + 发现类任务接力若干轮，乐观估 ~100/天。
- **问题**：里程碑「1 万家种子」若无官网（b2b 档案官网字段多数不填、搜索种子只收官网外延较少），官网发现要数百天才能消化积压，期间无官网线索富化不了、三问 who 无建联入口、进不了今日商机——「每天收到一批」冷启动期会结构性偏空。
- **结论**：建议追加裁决两条（任选/组合）：① CSV 种子导入**允许并鼓励带 website 字段**（LeadDraft 已支持，直接绕过官网发现，写前验证兜底）；② `_DISCOVER_LIMIT` 参数化（默认 30 保持礼貌约束，运营在冷启动期可显式调高）。

## 3. 技术可行性问题清单

### T1【A】Meta 免费 token 配额 vs 主页探测请求放大（无跨任务缓存）

- **证据**：FR-1.1 每词默认 2 页 × 100 广告，主页探测默认开；实现 `page_id` 只在**单次运行内**去重（`meta_ad_library.py:429`），无跨任务缓存。cron 轮转时同一批广告主每次任务都重新探测主页。
- **风险**：免费 token 有速率上限（数百请求/小时量级）；一个任务 = 搜索请求 + 数百次主页探测，多词多国轮转很快打满配额，任务 failed 或全库探测跑不完。
- **结论**：主页探测结果按 `page_id` 落库缓存（附探测时间，窗口内复用，如 30 天），与富化窗口分级同思路。这是纯免费约束下唯一可行的配额管理。

### T2【B】零 key 搜索通道（DDG → bing 中国）的长期可用性

- DDG HTML 端点有 bot 检测，bing 中国同样有风控，searxng 需自建实例（免费但增加运维面）。通道定位是**种子补充**（FR-1.2 默认关键词已被实测否决过一轮），主扩量靠 meta_ads + b2b——定位自洽。
- **结论**：可接受；要求任务失败率在数据源管理页可见（已有 failed 状态 + 日志），运营可观测即可，不追加工程动作。

### T3【B】无头浏览器「静默降级」的不可见性

- career_site 依赖薄壳 SPA 渲染；playwright 未装时静默降级，招聘信号漏检且无人知晓。
- **结论**：启动时 warning + 任务日志提示「浏览器未装，SPA 页跳过」。一行日志的事，不做功能改动。

### T4【B】单进程调度的可用性边界

- 进程崩溃期间错过的 cron 触发**不补跑**（APScheduler 默认语义）；重启后 running→failed、queued 保留（`task_runner.py:108-129`）。`WORKERS>1` 时调度自动禁用（`scheduler.py:29-32`）——若部署方无感地开了多 worker，「每天收到一批」静默断供。
- **结论**：运维文档（docs/运维部署.md）须显式声明「必须单 worker + 调度开关检查」。技术方案本身成立（§3 硬约束单进程）。

### T5【C】SQLite 备选模式并发——可接受

- DB 即队列 + 2 worker + 5s 进度写库，SQLite 写锁竞争存在但 WAL 模式可缓解；单进程设计恰好规避多进程冲突。生产默认 PG（`DB_TYPE` 切换）。**可行，无需动作**。

### T6【✓ 核实已解决】全库重评（口径迁移）的触发方式

- 一度不确定 §2.6「规则变更后全库重评走同一函数」如何落地——已核实 `backend/scripts/reeval_leads.py` 存在，走 `rescore_lead`（`lead.py:556`），与采集器同函数。**已解决**，只需把该脚本写进运维手册操作步骤。

## 4. 最终稳定结论

### 4.1 总体判定

**需求整体自洽、技术上可行、V1 已实现并通过测试。** 核心链路（发现 → 归一化去重 → ICP 门 → 14 信号加分制 → 三问 → 今日商机 → 领取跟进）逻辑闭环，无阻塞性缺陷。复盘发现的 4 个 A 级问题都是**边界条件与运维口径**问题，不推翻主设计；2 个 B 级是吞吐与指标口径；其余核实为无问题。
