# 线索采集系统 · 业务逻辑梳理

> 更新：2026-08-31（业务重构：ICP 二重门 + 每日商机批次 + 官网发现补全链 + 双产品线推荐）｜ 需求文档：`~/Downloads/whatsapp2`（终版）+ `~/Downloads/whatsapp`（早期版，六维公式出处）

## 1. 一句话定位（业务重构后）

**自动发现、评估并排序「最可能购买 WhatsApp 消息服务 + 出海 SaaS」的中国出海企业，让销售每天直接收到一批值得联系的客户**——不是企业名录，核心价值是回答：这家公司为什么需要你、应该卖什么、应该找谁。

- **客户只面向中国企业（做出海业务）**：ICP 二重门（`collectors/icp.py`）硬性准入，非中国企业不进销售池
- **招聘只面向中国招聘平台**：jobui 已落地（Playwright 渲染），BOSS/猎聘/前程/智联为 STUB
- **双业务线**：WA 消息（BSP 主线）+ 出海 SaaS + Meta/TikTok 广告代理（同客双报价）
- 链路：**采集 → 归一化 → 去重合并 → ICP 二重门 → 六维评分+分级 → 今日商机批次 → 领取 → 跟进建联 → 成交回传**

## 2. 核心数据流

```
meta_ads（主通道：广告库挖投放+主页探测 wa.me）─┐
web_search ──┤                                ├─→ LeadDraft ──→ 归一化 ──→ 三身份列反查 ──→ 新建/合并 Lead ──→ 评分+ICP 门落库
job_posting ──┼────────────────────────────────┘              (crud/lead.py)     (scoring.py + icp.py)
website_enrich ┘（直接改存量 Lead，不走 Draft；含官网发现补全链）
                                        ↑
                              手工录入 / CSV 种子导入（也走去重合并）

website_enrich 全库扫描 = 官网发现（无官网线索搜官网）→ 富化（出海/WA/SaaS 信号）
        → 重评（apply_score 同点重算 icp_status）→ 事件/预警
销售侧 = 今日商机批次（新晋 S/A + 新增高分 + 预警）→ 领取（claim）→ 跟进 → won 回传
```

## 2.5 ICP 二重门（资格判定，`collectors/icp.py`）

资格是**销售池准入门**，不是评分软加权（is_cn+45 已从出海维移除）：

| icp_status | 判定 | 动作 |
|---|---|---|
| `qualified` | CN 证据 + 出海证据 | 进销售池与今日商机批次 |
| `cn_domestic` | CN 证据、未见出海信号 | 培育池（补官网富化后升级） |
| `foreign` | 有评估结论但无 CN 证据 | **默认列表/导出排除**（`icp=all` 可显式看） |
| `unknown` | 证据不足（未富化） | 保留在池，标记待验证（不做有罪推定） |

- **CN 证据**（任一）：is_cn（中国招聘站来源 / CSV 中国种子 / meta_ads 中文页名 / 官网中文 ≥30% / **ICP 备案号**）｜country=CN｜+86 号码
- **出海证据**（任一）：overseas_signals 非空｜fb_whatsapp｜target_countries 非空｜**招聘信号含海外语义岗**（wa_ops/overseas_cs/overseas_sales/social_ops——2026-08-31 巡检补：在招海外岗 = 出海业务在运转的直接证据，jobui 通道无官网企业靠它进销售池，此前 24 家真实出海企业卡死培育池；crm_ops 不算，不必然出海）
- 「有评估结论」= enriched_at 非空 或 来源含 meta_ads——评估过才有资格 foreign
- 与评分同点重算（`apply_score` 写回），upsert/富化/联系人变更均触发；stats 有 `icp_counts` 四态分布

## 4. 采集器体系（插件式）

`backend/app/collectors/base.py` 定义契约：采集器实现 `run(ctx)`，通过 `ctx.emit(draft)` 落库、`ctx.log()` 写日志、`ctx.check_cancelled()` 响应取消。`collectors/__init__.py` 的 `_REGISTRY` 注册即接入任务体系/去重/评分，前端表单由 `param_schema` 动态渲染。

**param_schema 控件类型**（`type` + `options` 字段，2026-08-27）：`select`（可搜索下拉，国家/目标市场 15 国选项 + 允许手输）、`cities`（城市联动输入：`depends_on` 指向国家字段，选中后出该城市建议，仍可手输任意城市）、`tags`（标签输入，回车追加多个，提交时 join 逗号）、`multiselect`（预设选项多选）、`switch`（布尔开关，提交 `true`/`false` 字符串）、`number`（整数输入）、缺省 `text`（普通文本）。提交值统一序列化为字符串（后端 `split_csv`/`_parse_bool` 消费），必填校验前端先拦、后端 `validate_params` 兜底。

### 4.0 meta_ads（主通道：中国出海企业挖掘，2026-08-30）

ICP 反转后的核心获客链路——**挖「在投海外广告的中国企业」**：

- **入口**：Meta 官方广告资料库 API（`ads_archive`，v22.0），按「关键词 × 投放目标国」搜**在投**广告（`ad_active_status=ACTIVE`，必填 `ad_reached_countries`），每关键词翻页≤N（默认 2 页 × 100 条）
- **聚合**：按 `page_id` 去重广告主，记 page_name / profile_uri / 广告数 / 文案样本
- **主页探测**（`probe_pages` 开关，默认开）：双通道网络（系统代理优先——国内直连 Meta 域被墙；失败/软拦截切直连兜底）抓主页 HTML，提取：
  - `wa.me/<号码>` / `api.whatsapp.com/send?phone=` → **对方的 WhatsApp 号码**（销售建联第一入口，补 `+` 按国际号解析）+ `fb_whatsapp=True`（CTWA/私域运营证据）
  - 联系邮箱（复用 website_enrich 的检测与平台埋点黑名单）
  - 外链官网（解 `l.facebook.com/l.php?u=` 跳转 + 裸链接，滤平台域）→ 走 domain 去重
  - 中文特征（品牌名/文案含 CJK）→ `is_cn=True`（销售可筛「中国出海」）
- **只爬公司/企业**：主页类目标签（`categoryName`）命中非企业黑名单（公众人物/自媒体/媒体/政府/艺人/学校/宗教…，中英双语）→ 跳过不入库；企业类目映射中文存 `industry`（Shopping & Retail→零售 等）。拿不到类目（登录墙）保守放行——不误杀；探测关闭时无法判定类型，建议开着跑
- **CTWA 口径**：API 不暴露广告 CTA 类型（接口限制）；「主页挂 wa.me + 持续在投广告」= 已用 WA 做私域获客的可靠代理信号
- **凭据**：`META_ADS_ACCESS_TOKEN`（.env，**全程免费 0 元**：https://www.facebook.com/ads/archive/api 申请，Meta 开发者账号 + 建应用 + 生成 token 都不收费，无需投放广告，只需 ads_archive 只读权限）；缺失/无效（code 190）任务 failed 带指引，不产出空结果假成功
- **纪律**：主页探测间隔 ≥1.5s、翻页 ≥0.5s；单页探测失败记 warn 继续（登录墙/网络抖动不挡产出）
- `country` 语义：多国投放时统一记第一个投放国（单值列），明细看任务日志

### 4.3 website_enrich（富化，非采集源）

- **改存量线索**。范围 = `lead_ids` 指定（列表勾选入口）或全库「有网站 且 24h 内未成功富化」
- 每站点 ≤3 个请求（首页 + 最多 2 个同域联系页）；首页失败时最多再加 2 次回退（换 scheme、宽松 SSL 兜底）
- **抓取健壮性**：网络双通道（2026-08-31 起，详见 §4.5）——主 client 代理优先，宽松 SSL 兜底 client `trust_env=False` 直连。历史 P0（2026-08）：代理软拦截返回 202 造成「首页抓取失败」误报；现语义为「死代理 → 兜底直连仍成功」（回归测试本地回环验证）
- 检测：WhatsApp 指纹（wa.me / api.whatsapp.com / ht-ctc·joinchat·getbutton·chaty·elfsight 等插件特征）+ mailto 邮箱（资源文件名防误判）+ 5 平台社媒（FB/IG/LinkedIn/TG/TikTok）
- **场景 & SaaS 需求识别（2026-08-30）**：页面文本关键词命中（`collectors/scenes.py`，ASCII 整词 \b 词边界防 "about"误中"bot"）→ WhatsApp 场景（客服/营销/交易通知/SaaS）与 SaaS 信号（CRM/工单/Chatbot/AI 客服/营销自动化/全渠道），union 单调合并；抓到公开邮箱自动生成「待补全」联系人（`crud/contact.auto_create_from_email`）
- **号码证据链（补充需求 §4.1）**：`detect_whatsapp_numbers` 收集页面全部 wa.me 号码（去重）→ `whatsapp_numbers` 列表（多分线 = 规模化私域证据，参与 WhatsApp 维度加分）；meta_ads 主页探测同样累计
- **分级增量重爬（补充需求 §九）**：全库扫描按等级 S 1天 / A 3天 / B 7天 / C 30天；`ENRICH_INTERVAL_HOURS` 作 C 级兜底（默认 168h）；手动勾选不受限
- **只在成功抓到首页时写 `enriched_at`**——失败/超时下次自动重跑
- 两个入口一执行路径：列表勾选 → 隐式任务；手动/定时建任务 → 全库 eligible

### 4.5 website_enrich（富化 + 官网发现补全链，2026-08-31）

- **官网发现（全库扫描模式前置步骤）**：无官网且非 foreign 的线索（分数倒序、每轮上限 30、2s 礼貌间隔）→ 公司名走默认搜索引擎找官网（复用 web_search 的平台/文章页过滤与根 URL 归一）→ 写 website+domain（source=web_discovery, confidence=60）→ 本轮直接富化。否则 jobui 线索永远进不了富化/评分链路、cn_domestic 升不了 qualified
- CN 证据优先级：**ICP 备案号**（正则，+cn_icp 信号证据，防纯英文站误杀）> 中文内容 CJK≥30%

## 5. 去重合并（系统的心脏，`crud/lead.py:upsert_lead`）

1. **归一化**（`collectors/normalize.py`）：
   - 电话 → E.164（phonenumbers，用来源国兜底补国家码；解析失败不参与去重）
   - URL → registrable domain（tldextract 公共后缀表，www/路径/参数全剥）
   - 公司名 → 小写 + 去标点 + 剥法律后缀（Sdn Bhd / PT / Ltd / Pte…）
2. **主键优先级**：`domain:` > `tel:` > `namecity:`(md5(归一名+城市))；三键全空用 `raw:name|source` 兜底（宁漏勿重）
3. **跨来源合并的关键**：不能只比 draft 自己的主键——存量行主键可能是 `tel:`，新数据带官网进来是 `domain:`。用**三身份列（domain / phone_e164 / namecity_key）OR 反查**，任一命中即合并到最早那条；合并后主键升级收敛到 domain（有冲突则保留旧键）
4. **合并语义**：
   - 标量字段补空（country/city/website/email/phone…）
   - 布尔 OR（`whatsapp_hit` / `whatsapp_job`）
   - `job_urls` / `social` 并集
   - `last_ad_at` 取 max（最近投放开始时间，meta_ads 的 ad_delivery_start_time——2026-08-31 巡检接线，此前列恒空）
   - 来源记录按 `(lead, source)` 唯一 touch（cron 重复跑不膨胀）
   - **采集器带 email → 自动生成「待补全」联系人并重评**（2026-08-31 巡检：此前只有 website_enrich 富化路径这么做，meta_ads 抓的邮箱只落 lead.email 列，联系人维恒 0 分、详情页「应该找谁」空白；手工录入 source=manual 不自动生成）
   - 重算评分

存量行口径迁移：评分/ICP/export_type 规则变更后跑 `scripts/reeval_leads.py` 全库重评（与采集器写入同函数）。

实测：kalibrr 15 个岗位 → 10 条线索（同公司最多 3 岗位并 1 条 + 5 次合并）。

## 6. 意向评分 V2：六维加权（`collectors/scoring.py`，2026-08-30 重构）

**旧模型（8 布尔信号加和不封顶，最高 110）已废弃**——旧 95 分 ≈ 新 33 分，分值语义完全换轨，迁移 `b20022d59541` 已全量回填。新模型：

```
Lead Score = 出海×25% + WhatsApp×30% + SaaS需求×20% + 规模×10% + 营销活跃×10% + 联系人×5%
各维 0-100 封顶，总分四舍五入 clamp 0-100
分级：80-100=S（立即跟进）60-79=A（高潜力）40-59=B（培育池）0-39=C
```

| 维度 | 权重 | 规则（输入全是行属性，纯函数 `score_lead_inputs`） |
|---|---|---|
| overseas 出海 | 25 | **出海深度口径（2026-08-31 修正：CN 资格由 ICP 二重门承担，is_cn+45 已移除）**：`fb_whatsapp`+30、目标地区+15、官网+10、**≥3 国市场+10（meta_ads 投放 ∪ 官网 markets 提及合并计数）**、出海信号每类+7（cap 35） |
| whatsapp 意向 | 30 | **FB 私域(CTWA 代理)+25（黄金意向信号）**、`whatsapp_hit`+35、`whatsapp_url`+15、`whatsapp_job`+15（=wa_ops 同一事实只计一次，2026-08-31 修双计）、**多号码(≥2 分线)+10**、客服场景+10、营销场景+10 |
| saas 需求 | 20 | crm+22、helpdesk+22、chatbot+18、ai_service+18、营销自动化+12、全渠道+8、SaaS 场景+15（封顶 100） |

## 7. 任务生命周期

```
pending ──run/enqueue──> queued ──worker认领──> running ──┬─> completed
   ↑                                                      ├─> failed（业务异常/超时/重启中断）
   └──────────────── 再次执行 ←── cancelled ←──────────────┘
```

- **task_runner.py：DB 即队列**（无 Redis/Celery）。N 个 worker 协程（= `COLLECT_MAX_CONCURRENT`，默认 2）轮询 `UPDATE..RETURNING` 按 id FIFO 认领
- **采集流水线自动接力（2026-08-31 交互改造）**：发现类采集器（web_search/job_posting/meta_ads）任务成功完成 → 自动排入隐式 website_enrich 全库扫描（官网发现+信号复核+重评分）。种子要靠富化才有信号、才能过 ICP 门——这个先后依赖以前要用户记顺序手动跑两步，现在系统承担。`AUTO_CHAIN_ENRICH` 开关（默认开）+ `AUTO_CHAIN_ENRICH_INTERVAL` 节流（默认 60 分钟内跑过富化则跳过，防连环触发）。接力动作写入原任务日志（「已自动接力网站富化任务 #N」）
- 并发闸门满 = 新任务状态留 queued 自然排队，cron 触发**排队不失败**
- 执行期间进度/计数只写内存，收尾一次落库；`asyncio.wait_for` 超时（`COLLECT_TASK_TIMEOUT`）
- 取消 = 排队中直接 cancelled；运行中置 `cancel_event`，采集循环逐条 `check_cancelled()`
- **进程重启把 running 重置为 failed**
- **scheduler.py**：APScheduler 3.x，仅 `SCHEDULER_ENABLED=true` 的单进程启动（多 worker 只开一个）；cron 存 DB 重启自动恢复；`sync()` 全量重建 job（幂等），触发动作就是 `enqueue`

## 9. 关键设计取舍

| 决策 | 理由 |
|---|---|
| DB 做队列，无 Celery/Redis | 任务量级小（并发 2），重启不丢、零中间件 |
| 勾选检测 = 隐式任务 | 复用进度/取消/闸门/日志全套，两入口一执行路径 |
| 富化只记成功时间 | 失败站点天然可重试，不用单独失败队列 |
| 来源 (lead,source) 唯一 | 防 cron 定时跑把 JSON 数组刷爆 |
| 三身份列反查合并 | 单一 dedupe_key 无法覆盖跨键合并（tel 存量 + domain 新数据） |
| Crawlee 而非 Scrapy | asyncio 原生可嵌 FastAPI 后台协程；Scrapy 的 Twisted 与 asyncio 执行器冲突 |
