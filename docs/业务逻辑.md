# 线索采集系统 · 业务逻辑梳理

> 更新：2026-08-27 ｜ 需求文档：`/Users/zhangpeng/线索采集.md`

## 1. 一句话定位

给销售找「需要用 WhatsApp 做生意」的企业线索：**采集 → 归一化 → 去重合并 → 意向评分 → 列表筛选**。

## 2. 核心数据流

```
google_maps ──┐
job_posting ──┼─→ LeadDraft ──→ 归一化 ──→ 三身份列反查 ──→ 新建/合并 Lead ──→ 评分落库
website_enrich ┘（直接改存量 Lead，不走 Draft）              (crud/lead.py)     (scoring.py)
                                        ↑
                              手工录入（也走去重合并）
```

## 3. 领域模型（3 张表）

| 表 | 文件 | 关键字段 |
|---|---|---|
| `leads` | `backend/app/models/lead.py` | `dedupe_key`(唯一) + `domain`/`phone_e164`/`namecity_key` 三身份列；富化结果（`whatsapp_hit/url`、`email`、`social`、`enriched_at`）；`score`+`score_signals`；`sources`(JSON，按来源唯一) |
| `collect_tasks` | `backend/app/models/collect_task.py` | `collector`+`params`(JSON)、`cron_expr`、`is_implicit`、`status` 状态机、进度/新增/合并计数 |
| `collect_task_logs` | 同上 | 任务执行日志，FK 级联删除，`after_id` 增量拉取 |

## 4. 采集器体系（插件式）

`backend/app/collectors/base.py` 定义契约：采集器实现 `run(ctx)`，通过 `ctx.emit(draft)` 落库、`ctx.log()` 写日志、`ctx.check_cancelled()` 响应取消。`collectors/__init__.py` 的 `_REGISTRY` 注册即接入任务体系/去重/评分，前端表单由 `param_schema` 动态渲染。

### 4.1 google_maps

- Places API v1 Text Search（官方付费通道）
- 「关键词×城市」笛卡尔积拼 `{kw} in {city}`；每 query 最多 3 页（nextPageToken，约 60 条）
- 无 `GOOGLE_MAPS_API_KEY` 任务直接 failed
- 风险提示：Places API 条款对商家字段（非 place_id）有存储期限限制，商用前确认

### 4.2 website_enrich（富化，非采集源）

- **改存量线索**。范围 = `lead_ids` 指定（列表勾选入口）或全库「有网站 且 24h 内未成功富化」
- 每站点 ≤3 个请求（首页 + 最多 2 个同域联系页）；首页失败时最多再加 2 次回退（换 scheme、宽松 SSL 兜底）
- **抓取健壮性（2026-08 修复）**：httpx client 必须 `trust_env=False`——后端进程常继承系统代理（`all_proxy`），代理对目标站点软拦截（实测返回 202）会导致「首页抓取失败」误报；采集目标站一律直连。证书过期/自签的小站由宽松 SSL 兜底 client 第二次尝试
- 检测：WhatsApp 指纹（wa.me / api.whatsapp.com / ht-ctc·joinchat·getbutton·chaty·elfsight 等插件特征）+ mailto 邮箱（资源文件名防误判）+ 5 平台社媒（FB/IG/LinkedIn/TG/TikTok）
- **只在成功抓到首页时写 `enriched_at`**——失败/超时下次自动重跑
- 两个入口一执行路径：列表勾选 → 隐式任务；手动/定时建任务 → 全库 eligible

### 4.3 job_posting（招聘监控）

- kalibrr（PH/ID）用 Crawlee `BeautifulSoupCrawler` HTTP 直连，白拿重试/并发/请求管理
- 解析 `__NEXT_DATA__` → `pageProps.jobs[]`（2026-08 实测校准）
- **岗位帖 → 公司级线索**：同公司多岗位合并 1 条，`whatsapp_job` +30 只计一次，岗位 URL 存 `job_urls`
- `companyInfo.url` 按 host 分类：社媒 → `social`，否则 → `website`
- jobstreet_* 配置保留、启用即报错（Cloudflare 反爬，待 `pip install '.[collect]'` Playwright 支持）

## 5. 去重合并（系统的心脏，`crud/lead.py:upsert_lead`）

1. **归一化**（`collectors/normalize.py`）：
   - 电话 → E.164（phonenumbers，用来源国兜底补国家码；解析失败不参与去重）
   - URL → registrable domain（tldextract 公共后缀表，www/路径/参数全剥）
   - 公司名 → 小写 + 去标点 + 剥法律后缀（Sdn Bhd / PT / Ltd / Pte…）
2. **主键优先级**：`domain:` > `tel:` > `namecity:`(md5(归一名+城市))；三键全空用 `raw:name|source` 兜底（宁漏勿重）
3. **跨来源合并的关键**：不能只比 draft 自己的主键——存量行主键可能是 `tel:`，新数据带官网进来是 `domain:`。用**三身份列（domain / phone_e164 / namecity_key）OR 反查**，任一命中即合并到最早那条；合并后主键升级收敛到 domain（有冲突则保留旧键）
4. **合并语义**：
   - 标量字段补空（country/city/website/email/phone…）
   - 布尔 OR（`whatsapp_hit` / `whatsapp_job`）
   - `job_urls` / `social` 并集
   - 来源记录按 `(lead, source)` 唯一 touch（cron 重复跑不膨胀）
   - 重算评分

实测：kalibrr 15 个岗位 → 10 条线索（同公司最多 3 岗位并 1 条 + 5 次合并）。

## 6. 意向评分（`collectors/scoring.py`）

7 个布尔信号加权求和，满分 **110 不封顶**：

| 信号 | 权重键 | 分值 |
|---|---|---|
| 检测到 WhatsApp 插件/链接 | `whatsapp_plugin` | +40 |
| 在招 WhatsApp 客服/私域 | `whatsapp_job` | +30 |
| 有官网 | `has_website` | +10 |
| 有公开邮箱 | `has_public_email` | +10 |
| 位于高渗透目标地区 | `is_target_region` | +10 |
| 有电话 | `has_phone` | +5 |
| 有社媒主页 | `has_social` | +5 |

- `SCORING_WEIGHTS` env 按键覆盖；`TARGET_REGIONS` 默认 15 国
- 命中明细存 `score_signals` 供前端展示

## 7. 任务生命周期

```
pending ──run/enqueue──> queued ──worker认领──> running ──┬─> completed
   ↑                                                      ├─> failed（业务异常/超时/重启中断）
   └──────────────── 再次执行 ←── cancelled ←──────────────┘
```

- **task_runner.py：DB 即队列**（无 Redis/Celery）。N 个 worker 协程（= `COLLECT_MAX_CONCURRENT`，默认 2）轮询 `UPDATE..RETURNING` 按 id FIFO 认领
- 并发闸门满 = 新任务状态留 queued 自然排队，cron 触发**排队不失败**
- 执行期间进度/计数只写内存，收尾一次落库；`asyncio.wait_for` 超时（`COLLECT_TASK_TIMEOUT`）
- 取消 = 排队中直接 cancelled；运行中置 `cancel_event`，采集循环逐条 `check_cancelled()`
- **进程重启把 running 重置为 failed**
- **scheduler.py**：APScheduler 3.x，仅 `SCHEDULER_ENABLED=true` 的单进程启动（多 worker 只开一个）；cron 存 DB 重启自动恢复；`sync()` 全量重建 job（幂等），触发动作就是 `enqueue`

## 8. API 与前端

### API（`api/v1/endpoints/collect.py`，前缀 `/api/v1/collect`，全部 SuperUser）

| 端点 | 说明 |
|---|---|
| `GET /leads` | 筛选：国家/行业/来源/最低分/WhatsApp 检测/关键词（名称/邮箱/域名/电话/城市） |
| `POST /leads` | 手工录入（走去重合并） |
| `DELETE /leads/{id}` | 删除 |
| `POST /leads/check-whatsapp` | 勾选 → 创建隐式 website_enrich 任务，返回任务跳详情页 |
| `GET /collectors` | 采集器元信息（param_schema 动态表单） |
| `GET/POST /tasks`、`GET/PUT/DELETE /tasks/{id}` | 任务 CRUD（创建时校验参数；cron 存在则 sync 调度，否则直接入队） |
| `POST /tasks/{id}/run` / `cancel` | 执行 / 取消 |
| `GET /tasks/{id}/logs?after_id=` | 日志增量轮询 |
| `GET /stats` | 总数/WhatsApp 数/高意向数/活跃任务数 |

### 前端（`frontend/src/views/collect/`，Naive UI）

- **线索列表** `/collect/lead`：统计条 15s 轮询；6 维筛选；勾选 →「检测 WhatsApp」→ 隐式任务 → 跳任务详情；手工录入对话框；行删除
- **任务列表** `/collect/task`：创建对话框按 param_schema 动态渲染；cron 输入；活跃任务 3s 轮询自动刷新
- **任务详情** `/collect/task/:id`：进度条 + 日志 `after_id` 增量流；2s 轮询，任务到终态自动停；取消/再次执行

## 9. 关键设计取舍

| 决策 | 理由 |
|---|---|
| DB 做队列，无 Celery/Redis | 任务量级小（并发 2），重启不丢、零中间件 |
| 勾选检测 = 隐式任务 | 复用进度/取消/闸门/日志全套，两入口一执行路径 |
| 富化只记成功时间 | 失败站点天然可重试，不用单独失败队列 |
| 来源 (lead,source) 唯一 | 防 cron 定时跑把 JSON 数组刷爆 |
| 三身份列反查合并 | 单一 dedupe_key 无法覆盖跨键合并（tel 存量 + domain 新数据） |
| Crawlee 而非 Scrapy | asyncio 原生可嵌 FastAPI 后台协程；Scrapy 的 Twisted 与 asyncio 执行器冲突 |

## 10. 技术栈与依赖理由

| 依赖 | 用途 |
|---|---|
| Crawlee for Python 1.9（`[beautifulsoup]`） | 爬虫引擎；jobstreet 启用时装 `[playwright]` |
| httpx[socks] | Places API / 富化探测；SOCKS 代理支持（采集用户常挂代理） |
| phonenumbers | E.164 电话归一化（libphonenumber 官方移植） |
| tldextract | registrable domain（公共后缀表，去重键正确性依赖） |
| APScheduler 3.x | 定时调度（锁 <4，API 不兼容） |
